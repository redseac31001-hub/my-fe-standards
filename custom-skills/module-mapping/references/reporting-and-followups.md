# Reporting And Follow-ups

输出重点不是把脚本原始结果原封不动贴出来，而是把“模块边界 + 依赖风险 + 下一步动作”说清楚。

## Default Report Shape

```markdown
## 项目功能模块图谱

### 1. 摘要统计
- 总模块数
- 总文件数
- 总代码行数
- 平均健康度

### 2. 模块概览
| 模块 | 类型 | 文件数 | 行数 | 健康度 | 备注 |

### 3. 关键依赖关系
- 模块 A -> 模块 B
- 模块 C 存在循环依赖

### 4. 风险模块
#### 模块名
- 问题
- 原因
- 建议

### 5. 下一步建议
- 继续做结构审查
- 优先重构某个模块
- 暂不建议动结构
```

## What To Highlight

优先突出这些信息：

- 巨型模块
- 循环依赖
- 被过多模块引用的公共模块
- 明显越权引用或边界穿透
- 可以直接删除或归档的孤立模块

## Follow-up Mapping

| 发现 | 建议动作 |
|------|----------|
| 模块健康度普遍偏低 | 运行 `structure-review` |
| 某个模块内部组件过大 | 使用 `component-refactoring` |
| 只是需要项目导航图 | 输出图谱即可 |
| 依赖图复杂但边界还算清楚 | 先列观察，不急于建议大重构 |

## Guardrails

- 不要把所有模块都评成“建议重构”
- 不要只给图，不解释图的意义
- 不要把局部依赖问题夸大成全局架构失败
