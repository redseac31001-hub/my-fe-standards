# Scoring And Reporting

结构审查的重点不是输出一堆规则编号，而是明确回答四个问题：

1. 当前项目的工程健康度怎样
2. 结构本身是否健康
3. 问题主要集中在哪些地方
4. 现在适不适合动结构

## Mandatory Report Shape

```markdown
## 当前项目分析报告

### 1. 当前状态
- 审查范围
- 工程健康度总分
- 结构健康度
- 模块概览（如已执行 module-mapper）

### 2. 工程健康度评分卡（8 维）
| 维度 | 得分 | 状态 | 说明 |

### 3. 结构健康度（4 维）
| 维度 | 得分 | 说明 |

### 4. 关键问题
| 严重度 | 规则/类型 | 位置 | 问题 | 建议 |

### 5. 结论与建议
- 当前是否建议动结构
- 下一步最值得做的一件事
- 风险与前提
```

## Score Interpretation

### 工程健康度

| Score | 建议 |
|------|------|
| `>= 90` | 工程基础良好，主要保持即可 |
| `70-89` | 有局部短板，适合渐进修补 |
| `50-69` | 问题开始影响效率，建议规划改造 |
| `< 50` | 工程债已明显影响开发，应优先治理 |

### 结构健康度

结构健康度只反映这 4 个结构维度：

- 特性结构
- 目录深度
- 文件大小
- 命名规范

它不能单独代表整个项目健康度。

## Engineering Scorecard Dimensions

项目级分析默认展示以下 8 个维度：

1. 架构与目录结构
2. 代码质量
3. 类型安全
4. 测试覆盖
5. 依赖健康度
6. 构建与性能
7. 命名规范
8. 文档完整性

## When Not To Recommend Refactoring

以下情况要明确写“暂不建议动结构”：

- 距离发布很近
- 测试覆盖不足
- 当前有更高优先级故障
- 用户只是要一次诊断，不是要马上迁移

## Recommendation Mapping

| 观察 | 建议 |
|------|------|
| 局部目录混乱，但整体可控 | 小步迁移 |
| 新项目或测试完善，问题很集中 | 一次性迁移 |
| 历史包袱重、外部依赖复杂 | 适配层过渡 |
| 问题轻微 | 先保持现状，按功能演进慢慢修 |

## Guardrails

- 不要把分数当成唯一依据
- 不要给出“重构全部目录”这种空泛建议
- 建议必须和当前风险、测试、发布节奏挂钩
- 如果输出里只有“特性结构 / 目录深度 / 文件大小 / 命名规范”4 项，那只能叫“结构健康度”，不得冒充“项目总健康度”
- 如果脚本返回了 `scores.scorecard.dimensions`，报告必须按 8 维工程健康度评分卡组织
- 最终报告禁止包含“根据规则”“我应该”“接下来我会”等内部推理或过程性话术
- 报告提到孤立模块、低分模块、命名问题时，必须点名到具体模块或具体分项，不能只给数量和抽象判断
