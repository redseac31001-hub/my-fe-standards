# Scoring And Reporting

结构审查的重点不是输出一堆规则编号，而是回答三个问题：

1. 当前结构是否健康
2. 问题主要集中在哪些地方
3. 现在适不适合动结构

## Recommended Report Shape

```markdown
## 项目结构审查报告

### 1. 当前状态判定
- 结构类型
- 健康度评分
- 审查范围

### 2. 关键问题
| 严重度 | 规则/类型 | 位置 | 问题 | 建议 |

### 3. 结构判断
- 哪些目录组织合理
- 哪些地方存在反模式
- 当前主要瓶颈是什么

### 4. 改造建议
- 适合小步迁移 / 一次性迁移 / 暂不调整
- 风险
- 预估投入

### 5. 结论
- 现在该不该动结构
- 下一步最值得做的一件事
```

## Score Interpretation

| Score | 建议 |
|------|------|
| `>= 90` | 结构健康，主要保持即可 |
| `70-89` | 有局部问题，适合渐进修补 |
| `50-69` | 问题开始影响效率，建议规划改造 |
| `< 50` | 结构债已明显影响开发，应优先治理 |

## When Not To Recommend Refactoring

以下情况要明确写“暂不建议动结构”：

- 距离发布很近
- 测试覆盖不足
- 当前有更高优先级故障
- 用户只是要一次诊断，不是要马上迁移

## Recommendation Mapping

| 观察 | 建议 |
|------|------|
| 局部目录混乱，但整体可控 | 小步迁移 |
| 新项目或测试完善，问题很集中 | 一次性迁移 |
| 历史包袱重、外部依赖复杂 | 适配层过渡 |
| 问题轻微 | 先保持现状，按功能演进慢慢修 |

## Guardrails

- 不要把分数当成唯一依据
- 不要给出“重构全部目录”这种空泛建议
- 建议必须和当前风险、测试、发布节奏挂钩
