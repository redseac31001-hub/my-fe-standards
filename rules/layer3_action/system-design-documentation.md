# System Design Documentation (系统设计文档生成规范)

> Layer: Action
> Context: AI 根据模板、需求说明和项目上下文生成系统设计文档

<!-- @level:summary -->
## Summary (摘要)

生成系统设计文档时，必须以模板章节为骨架，以用户提供的事实材料为依据。缺失信息要显式标注，不得臆造接口编号、容量指标、安全方案、部署拓扑或运维承诺。

<!-- @level:quick -->
## Quick Reference (快速参考)

| 规则 | 要求 |
|------|------|
| **模板优先** | 章节顺序、标题层级、表格语义必须服从模板 |
| **事实优先** | 只写用户提供或代码/材料能支持的内容 |
| **缺口显式化** | 缺信息时输出 `待补充` 或待确认项 |
| **图文分离** | 没有图时先写图应表达的对象、边界和关系 |
| **表格可落地** | 表格列必须稳定，字段含义清晰 |

<!-- @level:full -->
## 1. Context (背景与适用范围)

该规则适用于系统概要设计、系统详细设计以及其他“模板驱动 + 正式文档导出”的设计文档场景。

## 2. The Rule (规则详情)

*   **Do**: 先识别模板章节和表格结构，再生成文档内容。
*   **Do**: 把需求说明、接口字段、页面说明、项目架构分别映射到明确章节。
*   **Do**: 对没有事实依据的内容输出 `待补充`、`待确认` 或图示说明要求。
*   **Don't**: 自行编造 SLA、RTO、RPO、容量峰值、接口编号、渠道编号、部署节点数。
*   **Don't**: 把详细设计内容混入概要设计，如数据库字段级设计、类级方法设计、逐接口字段映射细节。
*   **Preferred**: 图类章节优先输出“图应包含什么”和“关键关系说明”，再交由人工补图。

## 3. Reasoning (核心原理)

*   **Maintainability**: 模板驱动文档只有保持章节稳定，后续评审、归档和版本管理才可持续。
*   **Traceability**: 明确输入来源和缺口，可以降低 AI 文档“看起来完整、实际不可落地”的风险。
*   **Consistency**: 概要设计强调系统边界、能力与非功能目标，不应被详设细节污染。

## 4. Examples (示例)

### ✅ Good (推荐写法)

```text
性能目标：核心下单链路 P95 响应时间不高于 300ms。
说明：该指标来源于用户提供的非功能需求说明。
```

```text
部署架构图：待补充。
当前已知约束：生产环境部署在现有 Kubernetes 集群内，需跨双可用区。
```

### ❌ Bad (禁止写法)

```text
系统部署 12 个 Pod，单 Pod 4C8G，SLA 99.995%。
```

问题：用户未提供容量与 SLA 依据，属于编造事实。
