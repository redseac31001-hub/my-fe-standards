# Plans 目录规范

> 版本: 1.0 | 生效日期: 2026-01-27
> 本文档定义计划文件的创建、维护和状态管理规范。

---

## 核心原则

**Plans 是 Threads 的执行蓝图，Threads 是 Plans 的讨论记录。**

| 目录 | 职责 | 内容类型 |
|------|------|----------|
| `threads/` | 讨论过程 | 观点、评审、决策记录 |
| `plans/` | 执行蓝图 | 任务清单、验收标准、状态追踪 |

---

## 文件命名规范

### 强制对应关系

每个 Thread 必须有对应的 Plan 文件，采用相同编号：

```
threads/001-structure-analysis-enhancement.md
    ↓ 对应
plans/001-structure-analyzer-implementation.md

threads/002-mcp-server-optimization.md
    ↓ 对应
plans/002-mcp-server-optimization.md
```

### 命名格式

```
{编号}-{功能名称}.md

编号: 三位数字，从 001 开始
功能名称: 小写英文，用连字符分隔
```

## 创建流程

### 自动创建规则

当在 `threads/` 创建新讨论帖时，**必须同时**在 `plans/` 创建对应计划文件：

```markdown
## 创建新话题检查清单

- [ ] 在 threads/ 创建讨论帖 `{编号}-{名称}.md`
- [ ] 在 plans/ 创建计划文件 `{编号}-{名称}.md`
- [ ] 计划文件包含「需求验证」章节
- [ ] 计划文件关联讨论帖链接
- [ ] 更新 STATUS.md 添加新话题
```

### 计划文件模板

所有计划文件必须遵循以下结构（参考 `EXECUTION_PRINCIPLES.md`）：

```markdown
# {功能名称} 实施计划

> 计划编号: PLAN-{编号}
> 关联话题: [讨论帖标题](../threads/{编号}-{名称}.md)
> 创建时间: {YYYY-MM-DD}
> 状态: {状态标识}
```

## 状态管理

### 计划状态

| 状态 | 标识 | 说明 |
|------|------|------|
| 草稿 | 🟡 草稿 | 计划正在制定中 |
| 待批准 | 🟠 待批准 | 等待 Human 批准 |
| 已批准 | 🟢 已批准 | Human 已批准，可开始执行 |
| 执行中 | 🔵 执行中 | 正在实施 |
| 已完成 | ✅ 已完成 | 所有任务完成 |
| 已归档 | 📦 已归档 | 移至 archive/ |
| 已暂停 | ⏸️ 已暂停 | 暂停执行 |
| 已取消 | ❌ 已取消 | 计划取消 |

### 任务状态

| 状态 | 标识 | 说明 |
|------|------|------|
| 待开始 | ⬜ | 未开始 |
| 进行中 | 🔄 | 正在执行 |
| 已完成 | ✅ | 执行完成 |
| 已阻塞 | 🚫 | 遇到阻塞 |
| 已跳过 | ⏭️ | 决定跳过 |

### 状态更新规则

**AI 模型在执行任务后，必须立即更新对应状态：**

1. **开始任务前**：将任务状态改为 🔄
2. **完成任务后**：将任务状态改为 ✅
3. **遇到阻塞时**：将任务状态改为 🚫，并在讨论帖中说明原因
4. **Phase 完成后**：更新 Phase 状态，并在讨论帖中追加完成报告

```markdown
## 状态更新示例

### 更新前
| # | 任务 | 状态 |
|---|------|------|
| 1.1 | 创建类型定义 | ⬜ |

### 更新后
| # | 任务 | 状态 |
|---|------|------|
| 1.1 | 创建类型定义 | ✅ |
```

## 与讨论帖的同步规则

### Plans 是唯一真理源

**所有任务状态、验收标准以 Plans 文件为准，Threads 中的内容仅作讨论记录。**

| 内容类型 | 真理源 | 说明 |
|----------|--------|------|
| 任务清单 | `plans/` | Threads 中讨论的任务最终需同步到 Plans |
| 任务状态 | `plans/` | 状态变更必须更新 Plans 文件 |
| 决策记录 | `plans/` | Threads 讨论结论需记录到 Plans 的决策表 |
| 讨论过程 | `threads/` | 观点、评审意见保留在 Threads |

### 同步检查点

| 时机 | 操作 |
|------|------|
| 讨论达成决策 | 更新 Plans 的「决策记录」表 |
| 任务开始执行 | 更新 Plans 的任务状态为 🔄 |
| 任务执行完成 | 更新 Plans 的任务状态为 ✅ |
| Phase 完成 | 更新 Plans 的 Phase 状态，Threads 追加完成报告 |
| 遇到阻塞 | Plans 标记 🚫，Threads 记录阻塞原因和解决方案 |

## 归档规则

### 归档条件

满足以下任一条件时，计划应归档：

1. 所有任务状态为 ✅ 或 ⏭️
2. 计划被明确取消
3. 超过 30 天无更新且无活跃讨论

### 归档操作

1. 将 Plans 文件状态改为 📦 已归档
2. 将 Plans 和 Threads 文件移至 `archive/` 目录
3. 更新 `STATUS.md` 移除该话题

## 验收规则

### Phase 验收

每个 Phase 完成时，必须验证：

```markdown
### Phase X 验收检查

#### 技术验收
- [ ] 所有任务状态为 ✅
- [ ] 代码编译通过
- [ ] 测试覆盖达标

#### 用户价值验收（必须）
- [ ] 用户场景可完成
- [ ] 符合成功标准
```

### 计划验收

计划整体完成时，必须验证：

```markdown
### 计划验收检查

#### 需求验证回顾
- [ ] 目标用户覆盖
- [ ] 用户场景全部支持
- [ ] 宪章目标达成

#### 用户价值验收标准
- [ ] 全部通过
```

## 违规处理

### 检测点

1. **创建讨论帖时**：检查是否同时创建对应 Plans 文件
2. **任务完成时**：检查是否更新 Plans 状态
3. **Phase 完成时**：检查是否有用户价值验收

### 违规标记

```markdown
[Plans 规范违规] {违规描述}，请修正后继续。
```

## 变更管理规范

### 唯一真理源原则

**每个 Phase 的任务清单有且仅有一个位置。**

禁止出现以下情况：
- ❌ 同一任务在文件多处重复
- ❌ 验收标准与任务清单分离到不同章节
- ❌ 补充内容追加到文件末尾形成新章节

### 补充内容的正确处理

当需要补充或修改任务时：

1. **就地更新**：在原任务清单位置修改
2. **标注来源**：用引用块标注补充来源和日期
3. **更新版本历史**：在文件末尾版本历史表中记录

**正确示例**：

```markdown
### 任务清单

| # | 任务 | 验收标准 | 状态 |
|---|------|----------|------|
| 1.1 | 原任务 | 原标准 | ⬜ |
| 1.2 | 原任务 | 更新后的标准（含新要求） | ⬜ |
| 1.3 | 新增任务 | 新标准 | ⬜ |

> 2026-01-27 补充（来源：Codex 建议）：
> - 1.2 增加 XXX 要求
> - 新增 1.3 任务

### Phase X 验收标准

- [ ] 验收项 1
- [ ] 验收项 2（含新增要求）
```

**错误示例**（禁止）：

```markdown
### 任务清单
| # | 任务 | 状态 |
|---|------|------|
| 1.1 | 原任务 | ⬜ |

---

## ✅ 验收标准（文件末尾单独章节）
- [ ] 验收项...

---

## 🧾 补充检查清单（又一个新章节）
- [ ] 补充项...
```

### 结构一致性检查

每个 Phase 必须包含以下子章节（顺序固定）：

```markdown
## 📦 Phase X: 名称

**预估时间**: X 小时
**优先级**: 🔴/🟠/🟡
**状态**: ⬜/🔄/✅

### 任务清单
| # | 任务 | 验收标准 | 状态 |
...

> 补充说明（如有）

### Phase X 验收标准
- [ ] ...
```
