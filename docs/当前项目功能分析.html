1. 项目一句话¶

my-fe-standards 是一个可分发的 AI 辅助开发“规范 + 工具”平台：通过 codebuddy-loader 把 规则（Rules）、技能（Skills）、代理（Agents）、脚本（Scripts）、工作流（Workflow Spec）、任务书（TaskBook SSOT）、项目记忆（Reports） 与 Agent Call 文件协议 安装到业务项目的 .codebuddy/ 目录里，供 CodeBuddy/Claude Code/Amp 等工具按需读取并形成可审计的闭环执行。

核心入口： - 规则/工具分发：scripts/dist/codebuddy-loader.js（源：scripts/src/codebuddy-loader.ts） - 闭环编排：.codebuddy/scripts/task-orchestrator.js（源：scripts/src/task-orchestrator.ts） - 执行与质量闸门：.codebuddy/scripts/task-executor.js（源：scripts/src/task-executor.ts） - TaskBook 管理：.codebuddy/scripts/taskbook-manager.js（源：scripts/src/taskbook-manager.ts） - MCP 工具接口：mcp-server/src/index.ts

3. 核心概念与“数据对象”¶

3.1 三层规则（Rules）¶

  • Layer 1 Base（Eager）：被直接拼接进 .codebuddy/rules/project-rules.md，保证“核心规范常驻”。
  • Layer 2 Business（Lazy）：命中业务依赖才写入 .codebuddy/rules_cache/layer2_business/*.md，并在 project-rules.md 写索引。
  • Layer 3 Action（Lazy）：默认清单写入 .codebuddy/rules_cache/layer3_action/*.md，并在 project-rules.md 写索引。

相关实现要点： - 依赖识别：通过目标项目 package.json 检测 vue 版本与 ant-design-vue / vant 等依赖（scripts/src/codebuddy-loader.ts）。 - 规则裁剪：--rule-level summary|quick|full 只裁剪 Layer1 Eager 拼接内容；Layer2/3 的缓存文件仍保留原文（full）。（scripts/src/codebuddy-loader.ts）

3.2 .codebuddy/：业务项目的落地目录（SSOT 与证据）¶

典型结构（loader 生成/分发）：

.codebuddy/
├── rules/project-rules.md              # 主规则（含索引/说明）
├── rules_cache/                        # Layer2/3 原文缓存
├── skills/                             # Skills（SKILL.md + references）
├── agents/                             # Agents（AGENT.md + prompts/templates）
├── scripts/                            # 可执行脚本（taskbook/task-executor/...）

│   ├── taskbook.schema.json            # TaskBook 契约

│   └── history/*.json                  # 已归档 TaskBook
├── agent-calls/

    └── taskbooks/<id>.acceptance.json  # 验收报告（闭环产物）

3.3 TaskBook：任务协作的唯一事实源（SSOT）¶

  • 存储：.codebuddy/taskbooks/active/<taskBookId>.json
  • 契约：taskbooks/schema/taskbook.schema.json
  • 管理器：scripts/src/taskbook-manager.ts（支持 revision/锁、冲突检测、验收报告汇总）

TaskBook 关键字段： - status: draft → confirmed → executing → completed / aborted
- tasks[]: 原子任务（id/title/type/status/deps/acceptanceCriteria/scope/actualWork） - changelog[]: 变更与审计（包含 gate、batch、agent-call 事件）

3.4 Workflow Spec：闭环执行规范（DAG + gates + policies）¶

默认模板：workflows/templates/default.workflow.json（7 步闭环）： 1) requirement+prd（可跳过）
2) analyze（生成 reports）
3) plan（TaskBook 已存在时 no-op）
4) tdd_implement（按 batch 策略推进 + smoke gate）
5) review（人工 gate）
6) build_fix（checks gate + 自动回滚重试策略）
7) acceptance（验收报告 + 归档）

执行器：scripts/src/task-executor.ts 支持： - 拓扑排序 steps（基于 edges） - skipWhen 条件跳过 - gates（当前强制实现 checks，review 需要人工 --approve） - policies.concurrency 并行度与冲突策略（deny_same_file_set） - policies.testing.batching 分批策略（风险分层 + smoke gate 周期） - policies.buildFix 失败回滚与最大重试次数

3.5 Agent Call 文件协议：把“需要 AI/人工介入”变成可恢复阻塞¶

当执行器遇到需要外部执行的任务（MANUAL_REQUIRED），会： 1) 生成 .codebuddy/agent-calls/<requestId>.prompt.md 2) 将任务置为 blocked，并在 blockedReason 里附带一行元数据： - 形如：[agent-call] { ...json meta... } 3) 外部工具/人工写回 .codebuddy/agent-calls/<requestId>.result.json 4) 再次运行执行器时自动 apply：把 output.actualWork 写入任务并置为 done

4.3 质量闸门（gates）证据流¶

workflow step 执行到 gates（checks）时：
1) 执行 gate.params.commands / npmScripts（spawnSync shell）
2) 将执行结果写入：.codebuddy/reports/gates/<taskBookId>/<timestamp>.<stepId>.<gateId>.json
3) changelog 记录 gate 事件（便于 acceptance report 汇总）

review gate：
- 默认需要人工批准：task-executor 输出提示，要求使用 --approve <gateId> 继续

5. 功能清单（按域划分）¶

5.1 规则引擎（Rules）¶

  • Vue2/3 自动分流（通过 package.json 中 vue 版本与 @vue/composition-api 检测）
  • UI 库业务规范按需命中（ant-design-vue / vant）
  • Layer1 Eager 合并输出（支持 --rule-level 裁剪）
  • Layer2/3 Lazy 缓存 + 索引表（AI 任务需要时再读取缓存原文）

5.2 技能系统（Skills）¶

custom-skills/ 当前包含（以目录为准）： - frontend-code-review / component-refactoring / frontend-testing - build-optimization / performance-optimization - i18n-a11y / state-management - module-mapping / structure-review - prd / ralph-converter / skill-creator

落地方式： - loader 将 custom-skills/ 复制/下载到业务项目 .codebuddy/skills/ - 由 Agent/AI 按需读取 SKILL.md 并进一步加载 references/ 内容

5.3 Agent 系统（Agents）¶

当前 Agents（以 agents/ 目录为准）： - task-orchestrator：端到端闭环编排（MVP） - structure-analyzer：结构反模式检测 + 健康度评分 - planner：复杂任务分解/风险评估（输出 tasks 计划） - tdd-driver：RED→GREEN→REFACTOR 指引 - code-reviewer：结构化代码审查 - build-fix：构建/类型错误诊断修复（最多 3 轮策略在 workflow） - security-reviewer：安全审查（XSS 等） - performance-profiler：性能诊断（Web Vitals 等）

5.4 脚本工具链（Scripts）¶

loader 会分发 .codebuddy/scripts/（脚本清单在 scripts/src/codebuddy-loader.ts 中维护），其中关键脚本： - structure-analyzer.js：SA001–SA005 结构健康度 - module-mapper.js：模块识别/业务分类/（可选）依赖分析 - report-manager.js：reports 管理（status/diff/trend/cleanup/export） - taskbook-manager.js：TaskBook CRUD + plan/apply-plan + acceptance report 汇总 - task-executor.js：Workflow 驱动执行 + gates + batching + agent-call 协议 - task-orchestrator.js：一键闭环 runner（create→plan→confirm→execute） - contract-validator.js：契约校验（workflow/taskbook/agent-calls + batching scope 检查） - agent-call-manager.js：agent-call list/show/validate/serve（可选远程写回） - context-collector.js：收集目标文件内容 + 引用 + 关联测试 + Git 变更（注入 prompt）

5.5 MCP Server（对外工具接口）¶

mcp-server/src/index.ts 暴露： - Ralph：ralph_init/status/next/complete/add_story/log/set_workdir/ping - 结构分析：analyze_project_structure - CodeBuddy：codebuddy_set_workdir、taskbook_*、workflow_run、reports_inspect、reports_hotspots - Resources：ralph://prd、ralph://progress，以及 codebuddy://workdir、codebuddy://workflows/*、codebuddy://taskbooks/* 等

5.6 Ralph（自主编码）¶

两条路径： - scripts/ralph/ralph.sh：长循环（支持 amp/claude），以 <promise>COMPLETE</promise> 作为完成信号 - packages/agent/：ralph-agent（基于 @anthropic-ai/claude-code SDK），按 prd.json 用户故事迭代执行

6. 操作手册（真实场景）¶

下面的命令以“业务项目根目录”为工作目录（即 process.cwd() 指向业务项目）。

场景 A：业务项目首次接入（推荐远程一键）¶

1) 直接拉取并执行 loader（不需要把脚本落到项目）：

curl -fsSL https://raw.githubusercontent.com/redseac31001-hub/my-fe-standards/feature/codebuddy-glm/scripts/dist/codebuddy-loader.js | node - --remote https://raw.githubusercontent.com/redseac31001-hub/my-fe-standards/feature/codebuddy-glm

2) 生成物检查： - .codebuddy/rules/project-rules.md - .codebuddy/rules_cache/*（取决于命中依赖） - .codebuddy/scripts/task-orchestrator.js 等

场景 B：仅更新规则/脚本（升级规则库）¶

在业务项目根目录重复执行 loader 即可（覆盖更新为主）：

node path/to/codebuddy-loader.js --remote <REMOTE_BASE_URL>

建议把它固化到 package.json：

{ "scripts": { "rules:update": "node codebuddy-loader.js --remote <REMOTE_BASE_URL>" } }

场景 C：只把规则作为“常驻规范”使用（不走 TaskBook/Workflow）¶

运行 loader 后，AI 工具只需读取： - .codebuddy/rules/project-rules.md - 需要细节时按索引读取 .codebuddy/rules_cache/...

场景 D：项目结构审查（结构反模式 + 健康度）¶

node .codebuddy/scripts/structure-analyzer.js . --mode summary --output json

关注： - violations（SA001–SA005）与 score（分维度） - 结合 .codebuddy/reports/architecture/latest.json 做历史对比（若已启用 report-manager 的快照管理）

场景 E：模块图谱与业务域识别¶

node .codebuddy/scripts/module-mapper.js . --mode summary --output json

输出通常写入： - .codebuddy/reports/modules/latest.json

场景 F：TaskBook 手动使用（不走一键编排）¶

1) 创建 TaskBook：

node .codebuddy/scripts/taskbook-manager.js create --title "实现用户登录" --description "..." --type new-feature

2) 生成 planner prompt（写入 .codebuddy/agent-calls/）：

node .codebuddy/scripts/taskbook-manager.js plan <taskBookId>

3) 执行 planner prompt，并把结果写回 <requestId>.result.json（JSON，非 Markdown）。

4) 应用计划：

node .codebuddy/scripts/taskbook-manager.js apply-plan <taskBookId> <requestId>

5) 确认并执行：

node .codebuddy/scripts/taskbook-manager.js confirm <taskBookId>
node .codebuddy/scripts/task-executor.js <taskBookId>

场景 G：一键闭环（推荐）¶

node .codebuddy/scripts/task-orchestrator.js "实现用户登录功能" --type new-feature

常见阻塞与恢复： - 若输出 planner_result_missing：说明已生成 planner prompt，但 result.json 未写回
- 继续运行同一命令（或 --taskbook <id>）即可重试 - 若执行过程中出现 MANUAL_REQUIRED：会生成 .codebuddy/agent-calls/req-*.prompt.md，任务转为 blocked
- 写回 .result.json 后重新执行 task-executor/task-orchestrator 会自动 apply 并继续

（可选）Watch 模式：自动等待缺失文件出现后继续（适合“你在另一个终端/工具里写回 result.json”）：

node .codebuddy/scripts/task-orchestrator.js "实现用户登录功能" --watch

场景 H：质量闸门（gates）如何推进¶

  • checks gate：自动执行 commands / npmScripts，失败会阻塞；证据在 .codebuddy/reports/gates/<taskBookId>/...json
  • review gate：默认需要人工批准：
node .codebuddy/scripts/task-executor.js <taskBookId> --approve review_passed

场景 I：契约校验（避免多 Agent 写入不一致）¶

node .codebuddy/scripts/contract-validator.js --workflows --taskbooks --agent-calls

场景 J：远程模式完整自测（模拟真实用户）¶

node test/test-remote-full.js

场景 K：MCP Server 集成（给外部 AI 工具用）¶

在 mcp-server/ 下构建/启动（需要 Node >= 20）：

cd mcp-server
npm run build
npm start

之后外部 MCP Client 可调用 taskbook_* / workflow_run / reports_* 等工具，并通过 codebuddy://... 读取资源。

7. 扩展指南（怎么加能力）¶

7.1 新增/修改规则¶

1) 在 rules/layerX_*/ 下新增/修改 .md
2) （远程模式）执行 npm run build 更新 manifest.json
3) 业务项目重新运行 loader 拉取更新

7.2 新增 Skill¶

1) 在 custom-skills/<skill-id>/ 创建 SKILL.md + references/
2) 更新 manifest.json（npm run build）
3) 业务项目 rerun loader

7.3 新增 Agent¶

1) 在 agents/<agent-id>/ 创建 AGENT.md（可带 prompts/templates/checklists）
2) 更新 manifest.json
3) 业务项目 rerun loader

7.4 新增/调整 Workflow¶

1) 修改 workflows/templates/default.workflow.json 或新增模板
2) 如有 schema 变更，同步 workflows/schema/workflow.schema.json 与 contract-validator

8. 已识别的“一致性风险”（建议优先处理）¶

8.1 版本号多源不一致¶

当前仓库存在多个版本来源： - package.json / manifest.json：2.0.0 - README.md：2.3.0 - PROJECT.md：3.0.0

建议：明确单一事实源（SSOT），并在构建/发布时自动同步其余文档。

8.2 TaskType 契约与实现不一致（会影响闭环落地）¶

  • taskbooks/schema/taskbook.schema.json 的 taskType 只允许：analysis|design|test|implement|review
  • 但 scripts/src/types/index.ts 与 scripts/src/task-executor.ts 实际支持更多：requirement|prd|refactor|build-fix|acceptance 等
  • workflows/templates/default.workflow.json 也包含 requirement/prd/build_fix/acceptance 的 step 设计

建议：统一 TaskType 枚举（schema / planner 输出 / executor dispatch / MCP zod schema）后，再宣称“7-step 闭环”完整可执行。
